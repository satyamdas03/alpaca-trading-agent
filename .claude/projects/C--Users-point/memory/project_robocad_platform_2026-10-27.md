**Operational notes:** `docker` daemon not running on the laptop, so the container tier (4 `@pytest.mark.container` tests) is verified only by CI. The CI `sandbox` job builds `docker/executor.Dockerfile` and fails if any container test skips. Seven Linux-only defects have only ever been found there, never on Windows: (a) the Docker CLI was invoked with `env={"PATH": ...}` only, which breaks Docker Desktop — now `_runtime_env()`, a whitelist that forwards no secret; (b) `executor.Dockerfile` sets `ENTRYPOINT ["python"]`, so callers pass only flags plus the script path, never a literal `python`; (c) `resolve_within` was platform-dependent — `Path` made `C:\x` and `\\server\share` harmless-looking on Linux, so backslashes and drive prefixes are now rejected explicitly; (d) the mounted script sat in a `0700` dir the container uid could not traverse — it is now staged world-readable in a dir we own; (e) the same for `/out`, fixed by running as the caller's uid on POSIX (still non-root, root never mapped); (f) `test_container_cannot_read_host_env` failed on `GPG_KEY` from the base image — now uses a sentinel plus real secret names; (g) `_run_decomposed_generation` swallowed the executor error and returned `success=False, error=None` — the refusal message now reaches the response and `metadata.json`. Assume any sandbox change needs CI to be believed. `/health` is liveness (always ok); `/ready` is readiness (503 naming the missing env var) — do not merge the two back together. `pip install -e ".[dev,voice]"` is what CI installs; `[sim]` (mujoco) is optional and 7 tests skip without it. A laptop sleep mid-pytest can fail a heavy test with an empty traceback — that is environmental, rerun before chasing it.
